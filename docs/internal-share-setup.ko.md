# AIN 내부 공동 문서 운영 설정

운영 주소: `https://www.aincustoms.com/note`. 기존 `/internal`, `/internal/`은 새 주소로 이동한다. 홈페이지 메뉴·푸터에는 링크를 넣지 않는다.
비밀번호를 아는 사람은 모두 읽기와 편집이 가능하다. 표시 이름은 본인 확인된 계정이 아니다.

## 현재 구현과 배포 전 조건

- Yjs 기반 동일 문장 동시 편집, 한글, 개인 Undo, 편집/읽기 전환, URL 새 탭 열기.
- 캡처 후 본문에서 Ctrl+V 또는 도구막대 `이미지` 버튼으로 PNG/JPG/WebP를 첨부한다. 파일은 10MiB/약 3,200만 화소 이하, 브라우저에서 긴 변 2560px 이하·2MiB 이하의 정적 PNG로 자동 조정한다. 글자 판독에 영향이 있으면 필요한 영역만 잘라 캡처한다. 편집과 읽기 화면 모두 이미지가 표시된다.
- 이미지 업로드 중 노트를 전환하면 붙여넣기는 취소되며 다른 노트에 삽입되지 않는다. 실패해도 기존 글은 지우지 않는다. 일반 텍스트 붙여넣기·공동 편집·검색·되돌리기를 유지한다.
- 이미지는 별도 비공개 Storage 버킷 `internal-note-images`에 보관한다. 본문/Yjs/브라우저 암호화 저장본에는 짧은 이미지 참조만 들어간다. 직접 공개 주소·서명 URL을 제공하지 않고, 서버가 매번 현재 노트 세션을 확인한 뒤 이미지를 응답한다. 외부 이미지 URL·SVG·움짤은 렌더링하지 않는다.
- 왼쪽 `새 노트`로 제목과 카테고리를 입력해 노트를 만든다. 제목 옆 `이름·분류`로 변경한다.
- 카테고리별 노트 목록에서 선택한다. 각 노트의 본문은 분리되며 모두 같은 공유 비밀번호로 접근한다.
- 편집 도구의 `링크` 오른쪽 `본문 검색`에 입력하면 현재 노트의 첫 일치 위치로 이동하고 모든 일치를 강조한다. `↑/↓`, Enter/Shift+Enter로 순환 이동하며 `×` 또는 Escape로 지운다. 노트를 바꾸면 검색은 초기화된다.
- 약 1초 간격으로 작은 변경분을 전송/조회한다. 숨김 탭은 30초, 장애 때는 점진적으로 간격을 늘린다.
- 내용은 공개 HTML에 넣지 않는다. 브라우저에는 서버 저장 완료된 상태만 AES-GCM 암호문으로 보관한다. 매 접속 서버 인증 후 받은 메모리 전용 키로만 복원하며, 최신 변경사항 확인 전에는 읽기 전용으로 먼저 표시한다. 키·본문·노트 제목·커서는 평문으로 영구 저장하지 않는다.
- 첫 접속은 변경 이력을 최대 256개·약 3MiB까지 묶어 읽는다. 재방문은 암호화 저장본 이후의 변경분만 받으며 중복 초기 조회를 하지 않는다. 저장소/암호화 사용 불가 또는 손상된 저장본은 자동으로 서버 전체 조회로 전환한다.
- 초기 비밀번호 해시와 세션 서명키는 Vercel 서버 환경변수다. 최초 변경 후 비밀번호 해시는 서버 전용 DB에 저장하며, 매 요청 최신 상태를 조회한다. 설정 누락·DB 장애·비정상 상태는 503으로 닫고 예전 비밀번호로 되돌아가지 않는다.
- 저장소는 기존 Supabase의 **새 전용 테이블**이며 기존 요건/과세가격/화물 데이터와 분리한다.
- 초기 SQL/환경변수 설정과 단일 문서 운영 검증은 2026-09-16 완료했다. SQL을 다시 실행하지 않는다.
- 여러 노트 추가는 기존 Yjs 문서에 메타데이터/본문을 추가하는 방식으로, 별도 DB 마이그레이션이 없다.
- 로딩 개선에는 `supabase/migrations/20260917110000_internal_share_read_page.sql`을 1회 적용한다. 전용 읽기 함수만 추가하며 기존 문서·비밀번호·업무 DB를 변경하지 않는다. 서버 전용 권한, 고정 행수/용량 한도와 연속 커서를 검증한다.
- 이미지 기능에는 `supabase/migrations/20260922090000_internal_share_images.sql`을 1회 적용한다. 전용 비공개 버킷·메타데이터·서버 전용 예약/완료/읽기 함수만 추가하며 기존 노트 이력은 변경하지 않는다. 이미지 내용 해시를 키로 사용해 같은 이미지의 재전송은 중복 저장하지 않는다.

## 1. 전용 테이블 추가

기존 홈페이지가 사용하는 Supabase 프로젝트의 SQL Editor에서 다음 파일을 검토 후 1회 실행한다.

`supabase/migrations/20260916090000_internal_share.sql`

새 `internal_share_*` 객체만 만든다. 기존 업무 테이블/권한을 변경하지 않는다.
트랜잭션 단위로 실행하며, 이미 적용한 파일은 다시 실행하지 않는다.
비공개 테이블/RPC는 anon·authenticated 권한을 거부하고 service_role 서버만 허용한다.
Supabase 접근·실행을 이 작업에서 확인하지 못했다면 완료로 표시하지 않는다.

## 2. 초기 설정 및 화면에서 비밀번호 변경

이 프로젝트 폴더에서 `node scripts/create-internal-share-secret.cjs`를 실행한다.
원하는 비밀번호를 숨김 입력으로 두 번 입력한다. 채팅·GitHub·소스코드에 실제 비밀번호를 쓰지 않는다.

출력된 이름과 값을 Vercel 프로젝트 Settings → Environment Variables에 등록한다.

- `INTERNAL_SHARE_PASSWORD_HASH`
- `INTERNAL_SHARE_SESSION_SECRET`

기존 서버의 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`를 그대로 사용한다.
Production 설정을 확인한다. Preview 테스트는 별도 테스트 DB/별도 비밀번호를 사용하는 것이 안전하다.
위 생성기는 **최초 설치용**이다. 서버 전용 비밀번호 저장을 위해 `supabase/migrations/20260917090000_internal_share_password.sql`을 추가로 1회 적용한다. 초기 행은 revision 0/hash NULL이므로 기존 비밀번호를 바꾸지 않는다. 최초 화면 변경 이후에는 DB 해시만 비밀번호 검증에 사용한다.

운영 화면에서는 로그인 후 오른쪽 위 **설정**에서 현재 비밀번호, 새 비밀번호(6~128자), 새 비밀번호 확인을 입력한다. 현재 공유 비밀번호를 아는 구성원이 변경할 수 있으며 별도 관리자 계정은 없다. 변경 전에 현재 화면의 미저장 내용을 서버에 저장하고, 저장 실패하면 비밀번호 변경도 중단한다. 새 비밀번호는 새 salt를 사용한 scrypt 해시로만 저장하며 브라우저 영구 저장소나 로그에는 기록하지 않는다.

변경 후 시작되는 요청은 기존 쿠키를 거절한다. 구성원은 새 비밀번호로 다시 로그인해야 한다. 다른 구성원 화면에 남은 미저장 내용은 탭을 닫지 않고 다시 로그인하면 이어서 전송한다. 이미 서버에 도착한 요청은 변경 직후 완료될 수 있다. 응답 유실 시 변경이 완료되었을 수도 있으므로 새 비밀번호로 먼저 로그인한다. 비밀번호 변경은 원자적 revision 비교를 사용하므로 두 사람이 동시에 변경해도 하나만 성공한다.

비밀번호를 잊었을 때 DB를 초기화하거나 과거 env 비밀번호로 돌리지 않는다. 운영자가 검증된 서버 전용 경로로 새 해시를 설정하고 모든 세션을 무효화하는 별도 복구 절차가 필요하다.

## 3. 검증 후 배포

```
npm ci
npm run build:internal
npm run test:internal
```

브라우저 테스트 `scripts/check-internal-browser.cjs`는 Playwright와 설치된 Chrome을 사용한다.
테스트는 임시 비밀번호/메모리 저장소만 사용하며 운영 DB 검증을 대신하지 않는다.
Vercel 함수는 기존 cargo-admin의 엄격히 분리된 내부 경로에 위임하여 12개를 유지한다.
`/api/internal-share` rewrite와 GET/POST, 쿠키/CSRF를 Preview에서 실제 확인한 뒤 Production으로 반영한다.

운영 확인: 비인증 sync 401, 오답 비밀번호 거부, 정답 로그인, 두 브라우저 동시 편집,
새로고침 후 내용 유지, URL 클릭, 로그아웃 후 API 401, root 메뉴에 링크 없음.
기존 cargo-admin의 관리자 인증과 캘린더 cron도 변경 전후로 검사한다.

## 저장과 복구

- 저장 완료는 서버가 받은 것을 확인했을 때만 표시된다. 오류 때는 화면을 닫기 전에 내려받는다.
- `문서 내려받기`는 현재 노트의 Markdown 본문, `전체 노트 백업`은 모든 노트의 제목·분류·본문과 Yjs 상태·미저장 여부를 포함한 JSON이다.
- 서버 변경 이력은 덮어쓰거나 삭제하지 않는다. 하지만 같은 DB 안의 이력은 외부 백업의 대체물이 아니다.
- Markdown/JSON 내려받기는 노트 텍스트와 이미지 참조만 포함한다. 이미지 파일 자체는 포함하지 않으며 JSON에도 `imageFilesIncluded: false`로 표시한다. 오프라인 전체 복구에는 비공개 Storage 파일의 별도 백업이 필요하다. 본문에서 이미지 참조를 지워도 다른 노트/되돌리기를 위해 저장소 이미지를 자동 삭제하지 않는다.
- 이미지 저장은 전체 100MiB 또는 1,000개 예약까지 제한한다. 중단된 업로드 예약도 안전하게 한도에 포함되며 같은 이미지 재시도로 재사용한다. 한도 초과 시 자동 삭제·유료 증설하지 않고 명확한 오류로 중단한다. 저장소 정리는 별도 검토/승인 후 수행한다.
- 공유 문서에 중요 내용을 쓰기 전 Supabase 플랜의 백업/복구 범위를 확인하고, 주기적 외부 백업 위치·담당자를 정한다.
- 수동 복구: v2 JSON의 `notes[].text`(기존 v1은 `text`) 또는 내려받은 Markdown을 검토해 노트에 새 편집으로 반영한다.
  과거 Yjs 상태를 현재 문서에 단순 병합하는 방식은 과거 시점 복원을 보장하지 않는다.
- 브라우저 저장본은 속도 개선용이며 백업이 아니다. 서버가 확인한 완성 상태만 저장하므로, 저장 전 탭이 강제 종료되면 미전송 내용은 복구되지 않을 수 있다. 최신 내용 확인 실패 시 이전 저장본은 읽기 전용으로 남고 다시 연결한다. 인증 없는 오프라인 열기/편집은 제공하지 않는다.
- 로그아웃·세션 만료·비밀번호 변경 시 해당 화면의 브라우저 저장본과 메모리 키를 지운다. 비밀번호/서버 서명키가 바뀌면 복호화 키도 바뀌어 남은 옛 암호문은 열 수 없다. 비밀번호는 이전과 동일하며 이 기능이 임의로 재설정하지 않는다.
- 한 번에 붙여넣기 32KB, 노트별 본문 250KB, 단일 변경 전송 512KiB, 전체 노트 합산 서버 변경 이력 64MiB 한도. 큰 실행취소도 전송 한도 안에서 저장한다. 한도 초과는 저장 실패로 표시하며 자동 삭제하지 않는다.
- 화면에서 노트 100개까지 생성을 지원한다. 동시 생성 경합 때 이 수치는 엄격한 서버 상한이 아니며, 전체 저장 이력 제한은 서버에서 적용된다. 노트 삭제 기능은 제공하지 않는다.

## 운영 비용과 롤백

1초 조회를 8시간씩 월22일 유지하면 사용자당 약63만 회 API 요청이다. 실제 사용 인원에 따라
Vercel/Supabase 요청량과 요금을 확인한다. 장시간/다인원 사용은 WebSocket 전송으로 교체 검토한다.
유료 플랜 변경이나 외부 협업 서비스 구독은 자동으로 수행하지 않는다.

비밀번호 화면 변경 전 노트 배포는 `aincustoms-6rpcg1i9j-sukhyuns-projects-e670bc23.vercel.app`이다. **최초 비밀번호 변경 이후에는 이 구버전으로 롤백하지 않는다.** DB 해시를 모르는 구버전 코드는 예전 환경변수 비밀번호를 다시 허용한다. 이후 롤백은 반드시 이번 DB 기반 인증을 유지하는 버전으로 새로 배포한다.
롤백 시 `internal_share_*` 이력 및 credentials 행을 삭제하거나 revision을 0으로 되돌리지 않는다. 기존 노트 데이터는 그대로 보존한다.
과거 배포 URL도 Vercel 인증 보호를 유지해야 한다. 구버전 URL이 공개되면 그 서버의 환경변수 비밀번호로 현재 문서에 접근할 수 있다. 배포마다 과거 배포/프리뷰 주소가 비인증 요청을 Vercel 로그인으로 보내는지 확인하고, production 도메인이 새 배포만 가리키는지 검사한다.
노출 중지는 `INTERNAL_SHARE_PASSWORD_HASH`를 제거/교체하고 재배포하는 방법으로 차단할 수 있다.
기존 요건관리와 화물 DB를 되돌리거나 변경하지 않는다.

검증 참고: 이번 작업과 별개로 기존 nodemailer 9.0.6에 npm audit 보안 경고가 있다.
업무 메일 동작 변경을 피하기 위해 이 기능 작업에서 자동 업그레이드하지 않았다.
