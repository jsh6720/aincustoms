# 운영 데이터 불변 규칙

이 문서는 축산물 통관 대시보드의 기능을 수정할 때 기존 체크, 날짜, 요청, 메모,
수취 및 전달 상태를 유지하기 위한 필수 규칙이다.

## 핵심 원칙

1. 화면·레이아웃·기능 수정은 기존 운영 데이터를 변경하지 않는다.
2. API의 부분 업데이트는 요청에 명시된 필드만 저장한다.
3. 누락된 필드를 `false`, 빈 문자열, `null` 또는 기본 날짜로 바꾸지 않는다.
4. 새 컬럼이 아직 없는 환경의 폴백 조회는 실제로 없는 새 컬럼만 제외한다.
5. 서로 다른 계정에 연결된 동일 화물은 필드별 이력을 병합한다. 다른 필드의
   `updated_at`이 더 최근이라는 이유로 기존 O 상태를 X로 바꾸지 않는다.
6. 명시적인 O→X 변경은 해당 기능의 저장 API가 연결된 모든 현재 행에 같은 값을
   기록할 때만 반영한다.
7. 로컬 폴더 동기화는 화물 원천 데이터만 갱신한다. 홈페이지에서 입력한 체크,
   날짜, 요청, 메모 및 관리자 상태를 초기화하지 않는다.

## 구현 규칙

- `cargo_card_user_inputs` 조회 컬럼은
  `lib/cargo-user-input-query.js`의 단일 목록에서 관리한다.
- 마이그레이션 호환 폴백은 `TRANSPORT_CONFIRMATION_COLUMNS`만 제외한다.
- 서류전달 상태는 연결된 행 중 O 이력이 하나라도 있으면 O로 병합한다.
- 서류전달을 명시적으로 X로 바꾸는 API는 모든 연결 행을 X로 전파한다.
- 새로운 체크나 날짜 필드를 추가할 때는 다음 테스트를 먼저 추가한다.
  - 기존 O/날짜가 무관한 최신 수정으로 사라지지 않는 테스트
  - 부분 업데이트가 다른 필드를 보존하는 테스트
  - 마이그레이션 전 폴백이 기존 필드를 계속 조회하는 테스트

## 배포 전후 검증

1. 변경 전 Supabase의 해당 필드별 O 개수와 주요 BL 값을 읽기 전용으로 기록한다.
2. 전체 자동화 테스트를 실행한다.
3. 배포 후 동일 값을 다시 조회해 개수와 주요 BL이 유지되는지 확인한다.
4. 화면 API에서 기존 O/날짜/요청이 동일하게 반환되는지 확인한다.
5. 차이가 있으면 자동 보정하지 말고 배포를 중지하고 원인을 먼저 조사한다.

## 복구 원칙

- DB에 기존 값이 남아 있으면 데이터를 다시 쓰지 않고 조회·병합 코드를 수정한다.
- 실제 값이 사라진 경우에만 감사 가능한 대상 목록을 만든 뒤 복구한다.
- 복구 SQL 또는 스크립트는 실행 전후 행 수와 변경 대상 BL을 출력해야 한다.
