# HCH 수입신고 진행 자동 안내 설계

## 목적

로컬 유니패스 동기화에서 HCH 화물의 진행상태가 처음으로 수입신고 진행
단계에 진입하면, 기존 서류 관련 안내 메일 수신처에 해당 B/L의 수입신고가
진행되었다는 안내 메일을 자동 발송한다.

## 감시 대상

- 로그인 아이디가 정확히 `HCH`인 계정의 `cargo_cards` 행만 감시한다.
- 같은 원본 폴더를 조회하는 CTF, 삼현 및 다른 연결 계정 행은 감시와 발송
  건수에서 제외한다.
- HCH 행이 없는 B/L은 자동 안내 대상이 아니다.

## 상태 전환 규칙

- 새 진행상태가 정확히 `수입신고` 또는 `수입(사용소비) 심사진행`인 경우를
  신고진행 상태로 판단한다.
- `수입신고전`, `수입신고수리` 및 그 밖의 상태는 자동 안내 조건으로
  사용하지 않는다.
- 이전 HCH 행이 존재하고 이전 상태가 신고진행 상태가 아니며, 새 상태가
  신고진행 상태로 바뀐 경우에만 새 알림 이력을 만든다.
- 적용 시점에 이미 신고진행 상태인 기존 B/L에는 과거분 메일을 일괄
  발송하지 않는다.
- 한 번 발송 완료된 HCH B/L은 상태가 이후 변경되더라도 같은 유형의 안내를
  다시 발송하지 않는다.

## 수신처와 메일 내용

- 관리자 설정의 `H/C 원본 수령 확인` 메일 수신·참조 설정인
  `original_doc_receipt`을 그대로 사용한다.
- 계정별 출고요청 수신처와 요청인 메일은 자동 안내 수신처로 사용하지 않는다.
- 제목은 `[수입신고 진행 안내] 화주명 / B/L` 형식으로 한다.
- 본문에는 화주명, B/L, 납품처, 품명, 진행상태, 입항일, 반입구역,
  감지 시각을 포함한다.

## 저장과 중복 방지

- Supabase에 자동 상태 안내 이력을 보존하는 전용 테이블을 추가한다.
- 알림 유형과 정규화한 HCH B/L의 조합에 고유 제약을 두어 동기화 반복,
  서버 재시작 및 동시 실행에도 중복 이력이 생기지 않게 한다.
- 상태는 `pending`, `sent`, `failed`로 관리하고 발송 시각, 실패 사유,
  감지 당시 카드 정보를 저장한다.
- 메일 발송 실패 건은 다음 동기화에서 재시도하며, 성공한 건은 재시도하지
  않는다.
- 기존 카드, 요청, 서류, 날짜 및 관리 상태 데이터는 변경하거나 초기화하지
  않는다.

## 처리 구조

- 로컬 `sync_to_supabase.py`가 HCH의 기존 카드 상태를 업로드 전에 조회하고
  새 카드 상태와 비교한다.
- 상태 전환을 감지하면 알림 이력을 `pending`으로 등록한 뒤 기존
  `cargo-import-request` Vercel 함수의 내부 자동 안내 동작을 호출한다.
- Vercel Hobby의 함수 12개 제한을 지키기 위해 새 Serverless Function은
  만들지 않는다.
- 내부 호출은 로컬과 Vercel이 이미 보유한 Supabase service-role 키로 만든
  HMAC 서명과 짧은 유효시간을 사용한다. 원본 키는 요청 본문에 넣지 않는다.
- Vercel 함수는 서명, 알림 이력 및 HCH 계정을 다시 검증한 뒤 메일을 보내고
  결과를 알림 이력에 기록한다.

## 검증

- HCH 상태가 일반 상태에서 `수입신고`로 바뀌면 한 건을 발송한다.
- HCH 상태가 일반 상태에서 `수입(사용소비) 심사진행`으로 바뀌면 한 건을
  발송한다.
- `수입신고전`, `수입신고수리` 및 신규 생성 당시 이미 신고진행인 과거 카드는
  발송하지 않는다.
- 같은 B/L의 CTF·삼현 행이 바뀌어도 발송하지 않는다.
- 동일 HCH B/L을 반복 동기화해도 메일을 다시 보내지 않는다.
- 메일 실패 이력은 재시도하고 성공 이력은 재시도하지 않는다.
- 메일 수신처는 `original_doc_receipt` 설정을 사용한다.
- 기존 Node 회귀 테스트와 로컬 Python 동기화 테스트가 모두 통과한다.
