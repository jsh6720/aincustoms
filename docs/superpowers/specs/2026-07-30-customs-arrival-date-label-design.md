# 관세청 실제 입항일 표시 설계

## 목표

관세청 화물조회에서 실제 입항일이 확인된 건은 수기 입항예정일보다 실제 입항일을 우선 표시하고, 날짜 뒤에 `(관세청)`을 붙여 출처를 명확히 한다.

## 표시 규칙

- 관세청 실제 입항일(`entry_date`)이 있으면 `YYYY-MM-DD (관세청)`으로 표시한다.
- 실제 입항일이 없으면 수기 입항예정일(`eta_date`)을 표시한다.
- 둘 다 없으면 기존 최초 입항일 대체값을 사용한다.
- `(관세청)` 표시는 BL별 진행현황과 대시보드 요약 카드에 적용한다.
- 캘린더는 날짜 칸 자체가 출처를 설명하므로 기존처럼 날짜와 이벤트명만 표시한다.

## 편집 규칙

- 운송/반입예정정보 편집창의 입항예정일 입력값은 수기 저장값(`eta_date`)을 우선 불러온다.
- 수기 저장값이 없을 때만 관세청 실제 입항일을 입력 기본값으로 사용한다.
- 저장 비교도 수기 저장값 기준으로 수행해 실제 입항일 때문에 변경 감지가 왜곡되지 않게 한다.
- 수기 입항예정일을 저장해도 관세청 실제 입항일은 수정하거나 삭제하지 않는다.

## 자동 확정 규칙

- 관세청 실제 입항일(`entry_date`)이 있으면 입항일은 자동으로 확정 상태로 판정한다.
- 자동 확정은 기존 수기 확정값(`eta_date_confirmed`)을 삭제하거나 덮어쓰지 않고, 조회 결과에서 우선 적용한다.
- 관세청 실제 입항일이 있는 동안에는 수동으로 미확정 상태로 되돌려도 다음 조회에서 자동 확정으로 복원한다.
- 실제 입항일이 없는 건은 기존 수기 확정/해제 기능을 그대로 사용한다.

## 데이터와 배포

- Supabase 컬럼 추가나 데이터 마이그레이션은 필요하지 않다.
- 기존 `entry_date`와 `eta_date`를 그대로 사용한다.
- 표시 함수, 편집창 초기값, 변경 비교 로직과 조회 단계의 확정 상태 판정만 수정한다.

## 검증

- 실제 입항일과 수기 예정일이 모두 있으면 실제 입항일과 `(관세청)`이 보이는지 확인한다.
- 실제 입항일이 없으면 수기 예정일만 보이는지 확인한다.
- 실제 입항일이 있으면 입항일이 자동 확정 표시되는지 확인한다.
- 실제 입항일이 없는 건은 기존 수기 확정/해제가 유지되는지 확인한다.
- 편집창은 수기 예정일을 유지하는지 확인한다.
- 저장 후에도 실제 입항일이 변하지 않는지 확인한다.
- 전체 자동화 테스트와 프로덕션 배포 상태를 확인한다.
