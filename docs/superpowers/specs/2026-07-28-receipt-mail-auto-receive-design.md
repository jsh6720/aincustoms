# 수령메일 발송 시 원본서류 자동 수취 처리 설계

## 목표

관리자가 `H/C 수령메일`을 성공적으로 발송하면 해당 B/L의 OBL과 H/C를 모두 수취 완료로 저장하고, 메일 송신일을 실제 수령일로 기록한다.

## 적용 범위

- 관리자 대시보드와 모바일 원본서류 페이지의 `H/C 수령메일`
- `cargo-original-doc-receipt-mail` API의 `hc_receipt` 동작
- 동일 화물로 연결된 관리자, 화주, 납품처 계정의 원본서류 상태
- 모바일 원본서류 페이지의 업무 우선순위 정렬

`OBL 선사 접수 확인` 메일은 기존 동작을 유지한다.

## 처리 순서

1. 관리자 세션과 입력값을 검증한다.
2. 기존 수령 확인 메일을 발송한다.
3. 메일 발송이 성공하면 한국 시간 기준 송신일을 `YYYY-MM-DD`로 계산한다.
4. 요청한 카드와 동일한 B/L 및 폴더로 연결된 카드 계정을 찾는다.
5. 연결된 모든 계정의 `cargo_original_docs` 레코드를 다음 값으로 upsert한다.
   - `obl_received: true`
   - `hc_received: true`
   - `actual_received_date: 메일 송신일`
   - `updated_by: 관리자 로그인 아이디`
6. API 응답에 수령일과 저장된 상태를 포함한다.
7. 관리자 대시보드와 모바일 페이지는 성공 후 데이터를 다시 불러와 OBL/H/C `O`와 수령일을 즉시 표시한다.

## 오류 처리

- 메일 발송이 실패하면 원본서류 상태를 변경하지 않는다.
- 메일 발송 후 DB 저장이 실패하면 API는 부분 성공 오류를 반환한다.
- 부분 성공 오류 문구에는 메일이 이미 발송됐음을 명시해 관리자가 같은 메일을 중복 발송하지 않도록 한다.
- 연결 계정 중 일부만 저장되는 상황은 성공으로 처리하지 않는다.

## 구현 구조

- 연결 카드 검색과 원본서류 상태 upsert를 재사용 가능한 서버 유틸리티로 분리한다.
- 기존 `cargo-original-docs` API와 같은 연결 기준인 `B/L + folder_name`을 사용한다.
- 메일 API는 메일 발송 성공 후 유틸리티를 호출한다.
- 프런트엔드는 별도 저장 API를 연속 호출하지 않고 메일 API의 단일 결과만 사용한다.

## 검증

- H/C 수령메일 성공 시 OBL/H/C가 모두 `true`로 저장된다.
- 수령일은 한국 시간 기준 메일 송신 날짜다.
- 동일 화물의 연결 계정 모두 같은 상태와 날짜를 갖는다.
- SMTP 실패 시 DB 쓰기가 발생하지 않는다.
- DB 저장 실패 시 부분 성공 안내를 반환한다.
- OBL 선사 접수메일은 원본서류 수취상태를 변경하지 않는다.
- 관리자 및 모바일 화면은 성공 후 새 데이터를 다시 불러온다.

## 모바일 정렬

모바일 원본서류 페이지는 다음 순서로 표시한다.

1. 화주 수령요청이 있고 아직 원본서류 수령이 완료되지 않은 건
2. OBL과 H/C가 수령 완료됐지만 OBL 선사 접수일이 없는 건
3. 입항 또는 반입 단계이면서 OBL이나 H/C가 미수령인 건
4. 그 밖의 일반 건
5. 화주 수령요청과 원본서류 수령 및 OBL 선사 접수까지 완료된 건

같은 우선순위에서는 화주 요청 건은 최신 요청 순, 나머지는 B/L 오름차순으로 정렬한다.
